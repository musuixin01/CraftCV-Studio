# CraftCV-Studio 简历生成统一规范（RGS）

版本：1.1（四模块实施规范）
状态：**规范已制定；不是声明所有规则均已写入运行时代码**
适用范围：简历文件解析、GitHub 工程提炼、AI 润色、统一写作规则、JD 匹配、简历定稿、模板排版、PDF/JSON 导出和质量检查。
适用场景：实习、校招、社招、转岗、资深岗位及跨行业简历；国内技术岗位是既有模板示例而非全产品强制默认。英文简历、学术 CV 和海外投递保留目标地区/行业特殊格式配置。
本文件是后续研发时的**唯一简历生成规则来源**。项目的不同 AI 端点提示词、模板与用户自定义润色侧重点，均不得突破本文定义的安全与真实性边界。模板只负责呈现，不能自动修改事实。

**技能库清空决定（2026-11-09）**：保留 AI 技能库页面及未来新建、导入、编辑、自选、自动匹配能力，但首次打开更新后的应用时，对该浏览器站点存储执行**一次性清空**：只清除 `craftcv_ai_skills_v1`、`craftcv_selected_skill_ids_v1`、`craftcv_auto_skill_mode_v1`，并写入一次性完成标记 `craftcv_ai_skills_reset_20261109_v1`。此前所有内置与自定义 AI 技能包不再被使用；清空完成后新创建的自定义技能继续持久保存，绝不可重复清空。不得清除简历正文、岗位版本、母版附件、模型配置或其他站点数据。没有技能包时使用独立的核心简历写作规范与事实守卫，正常生成、润色与精简。此清理会丢失旧技能包文本，仅因用户明确要求清空才执行。## 1. 产品目标与原则

**产品承诺：用已有材料快速生成可信、岗位相关、可编辑、可投递的高质量简历。**

目标不是制造更长的内容、追求更高的虚构 ATS 分数或用复杂的 UI 模拟专业感。按以下顺序取舍：

1. 数据安全、隐私、授权；
2. 内容真实性与准确性；
3. 用户确认与可回退；
4. 岗位相关性和技术深度；
5. 版式正确、可阅读、可解析；
6. 生成速度、交互效率和视觉审美。

**禁止以节省操作为由自动补造事实。** 允许自动处理空白、重排、措辞和版面；未经确认，不自动增加工作经历、技能、技术成果、量化指标、竞赛名次、毕业时间或实测结论。

### 1.1 跨行业、跨年资的统一写作尺度

本规范覆盖实习、应届招聘、社会招聘、资深岗位、转岗及不同专业领域。**真实性是底线，不是要求所有内容都提供第三方鉴定**。本人在旧简历或编辑器中明确陈述的职责和实际做过的工作，可以正常进入候选稿并进行专业润色；除明显冲突与高风险数字外，不强制每一句都补证书、视频或测试日志，也不因暂缺证据而机械降级为“参与、尝试、待验证”。

- **有力度的表达**：用实际动作、解决的问题、技术/业务方法、协作范围和交付价值体现能力。可以合理整合、概括和强调成果，不添加新的责任边界或完成状态。
- **按岗位而变**：技术岗强调架构、实现、排障；运营/市场强调策略、执行与业务影响；设计岗强调研究、设计决策和落地；管理岗强调团队协作、交付与组织成果；学术简历强调研究方法与论文/科研事实。这些只是展示侧重点，不是凭空补造内容。
- **按年资而变**：实习和应届优先真实实践与学习成果，社招优先实际岗位职责、项目交付、业务价值；管理与专家岗位突出真实决策和影响范围。不能默认每个人都是应届电子信息工程师。
- **有数写数、无数讲价值**：已有可解释的指标可以正常使用；没有数字不影响写清功能、难题、流程优化和真实交付。STAR/XYZ/FAB 不是必填模板。
- **异常才核对**：身份资质错误、日期冲突、凭空增加的技能/职责、虚构数值和将未完成说成正式验收等应阻断或提示；普通本人自述无需因无第三方证明而判为造假。
- **篇幅适配场景**：一页精简只是一个模式，不是全产品强制规范。高年资、研究型和多项目岗位允许内容合理扩展，最终排版仍须验收。

生成、单项润色、JD 定制、内容精简和 GitHub 草稿均直接遵循此标准；自定义指令可以调节风格，不能突破事实边界。用户手工确认内容后的权威事实状态与外部机构认证保持区分。

### 默认的最短用户流程

- 第一步「导入」：旧简历、用户手填内容、允许访问的 GitHub 公开项目；可选目标 JD。
- 第二步「核对」：只展示真正影响投递的缺失、冲突和 AI 新建议，逐项确认或忽略；不要求用户重填已知字段。
- 第三步「完成」：选择模板、即时预览、质量检查、输出正式版；可继续点按修改或拖动排版。

首次使用无材料时直接进入可填写的空白简历，不用强制导入。所有流程均保留退出、取消、重试及恢复现有版本的能力。用户不选择 JD 时生成通用基础版，不擅自猜测具体公司的要求。

## 2. 适用情景与长度

| 情景 | 默认组织 | 建议版式 | 说明 |
| --- | --- | --- | --- |
| 国内应届/实习·技术岗位 | 教育、技能、项目、实习、奖项，以岗位相关性调整顺序 | A4 单页优先 | 不是不可突破的硬性页数限制，信息较多可明确采用两页 |
| 国内有经验技术岗位 | 经历和可核实的业务/技术成果优先 | 1–2 页，随实际年资/内容调整 | 不为了凑一页缩到不可读 |
| 海外技术岗位 | 遵循目标国家与机构的实际要求 | ATS 友好单栏通常优先 | 默认不展示性别、年龄、照片等非必要个人信息 |
| 学术 CV / 研究申请 | 教育、研究、发表、科研和学术成果 | 可以多页 | 与求职 Resume 的字段、结构和评价规则分离 |

国内校招中照片默认可选；政治面貌、年龄、性别、籍贯、身份证件号等敏感字段绝不自动推断，也不作为必填。无岗位必要性时不主动建议收集不必要的敏感数据。

### 一页纸原则

- 校招默认推荐 A4 单页，但**以完整、可读、真实为前提**；内容明显超页时先精简冗余，不静默删掉高价值内容。
- 字体、留白、线条、对比和标题等级由设计系统统一控制；不允许通过极小字体、挤压行距、裁掉最后一条成果来假装单页。
- 显示分页预警，并给出「缩短措辞 / 调整间距 / 改为多页」三个可回退选项，不能默认擅自改动所有模板。

## 3. 资料来源、证据级别与责任归属

每条能影响招聘判断的内容都应知道来源及核实状态。**来源有证据，不等于证明申请人独立完成了该工作。**

### 3.1 统一来源等级

| 等级 | 例子 | 可以做什么 | 不允许做什么 |
| --- | --- | --- | --- |
| A·已核验 | 用户提供的学校成绩单、奖状、原始实验报告、测试记录；可复核的公开文件 | 抽取对应事实，保留日期、口径和来源位置 | 由成绩单推断 GPA，或把代码配置值当实测结果 |
| B·用户声明 | 旧简历、个人填写的项目职责、在用户确认后的经历 | 作为「用户自述」写入草稿；必要时请用户核实 | 对外声称已由 GitHub 或第三方独立证实 |
| C·工程线索 | GitHub README、目录、源码、Commit、Issue、测试代码 | 证明仓库存在相应代码/接口/设计线索 | 自动断言本人贡献、实物运行、生产上线、性能提升 |
| D·AI 建议 | 改写草稿、JD 推断的关键词、推荐措辞 | 作为候选建议，等待确认和来源匹配 | 当作新增事实或证据写进正式简历 |
| U·未知/冲突 | 缺失任职时间、成果指标不一致、学历字段不清 | 保留空白、标注需确认、提供来源对照 | 猜测补齐、无提示地覆盖较早版本 |

其中「A」并不意味着全面真实性审计，只表示可追溯至材料。来自公开仓库的代码可能由团队、开源贡献者、自动生成器提交，**不能单独证明个人负责范围**。涉及身份、实际职责、最终成果的字段，仍须用户核对。

### 3.2 研发所需的非破坏性事实模型（拟新增，不替换现有 ResumeDocument）

建议在现有简历数据之外并行维护可选元数据，每条事实至少包括：

- factId：稳定标识。
- path：指向简历字段或项目要点（如 projects[项目 id].bullets[要点 id]）。
- claimType：education / role / skill / action / metric / outcome / award / date。
- originalValue：原始资料表达；normalizedValue：规范化后的表达。
- sources：源材料 ID、文件片段或文件/提交路径、定位信息、访问权限和采集时刻。
- status：verified-source / user-asserted / inferred-suggestion / missing / conflicting。
- candidateConfirmed：本人是否已确认此项描述。
- editedAt、versionId：最后变更与简历版本。
- sensitivity：是否含私密/凭证信息；是否允许发送云端模型。

实现时必须兼容旧 ResumeDocument、旧版 JSON 和已有 localStorage。新增元数据为可选字段；不能让历史数据在迁移时无声丢失或被自动认定为已验证。


### 3.3 结构化数据契约：内容、设计、语言、输出和事实记录

参考 RenderCV 将 cv、design、locale、settings 分离的结构，但**不将 RenderCV 的 YAML 或 Pydantic 实现直接搬入项目**。CraftCV 应在已有 ResumeDocument 外定义以下概念边界，保持旧版数据可正常加载：

| 逻辑对象 | 权威内容 | 不负责的内容 | 最小关联 |
| --- | --- | --- | --- |
| ResumeContent | basics、education、projects、experience、skills、awards、customSections、sections 内容与顺序 | 不知道模板配色 | 现有 ResumeDocument 对应内容字段 |
| ResumeStyle | 模板 ID、字体、颜色、行高、间距、页面与栏宽 | 不修改学校、学历、技术成果 | 现有 ResumeDocument.style |
| ResumeLocale | 语言、地区、日期标签、默认纸张习惯、隐私字段展示规则 | 不翻译成未经核实的学历和证书名称 | 新增可选配置；旧数据采用现有中文默认 |
| ExportSettings | PDF 类别、导出路径/文件名、页数策略、字体与文本检查选项 | 不创建新简历内容 | 导出时配置，不持久化覆盖原稿 |
| FactLedger | 来源、证据类型、本人确认、版本、冲突及敏感级别 | 不等于对外宣称「第三方认证」 | 第 3.2 节的可选事实元数据 |
| ValidationReport | 校验问题、严重性、字段路径、建议处理及回退动作 | 不直接写回事实 | 第 8.5 节的质量审核结果 |

**数据设计 D-01 至 D-09**

D-01：从 PDF、图片、DOCX、JSON 或 GitHub 导入时，先得到「原始输入 → 解析草稿」，不得在同一步自动生成未知工作经历与项目成果。当前尚未实现 DOCX 直接导入，相关规则只是目标契约。

D-02：保留用户已有 ResumeDocument 与原始 JSON 的兼容性。新增字段应可选并带版本号；旧内容加载时不能注入演示姓名、学校、项目、照片或夸大措辞。

D-03：结构校验与事实核验分离。字段类型、数组结构、ID 唯一性、合法日期格式、模板 ID 和允许的 URL 协议由确定性校验处理；「这项经历是否真实」必须由来源及本人确认处理，**不准用 JSON 结构有效来代替事实真实**。

D-04：日期支持 YYYY、YYYY.MM、至今及明确标注的未知状态；校验开始/结束的先后顺序，不凭缺少月份推定精确日期。允许不同时间段经历重叠，重叠只是提示，不能自动判定造假。

D-05：量化信息必须区分 measured（实测值）、configured（配置参数）、estimated（明确标注估算）、claimed（用户声明）、unknown（未知）。建议记录数值、单位、上下文和依据；没有依据不补百分比或「零误差」等说法。

D-06：允许保留多源冲突。例如成绩单与旧简历数字不同，报告应同时提供原值、来源及日期，让用户选择；不按更大、更漂亮或更新的数字自动取舍。

D-07：字段更新必须是可审阅的 patch/diff，带源数据版本号、目标 ID、修改前后值、来源及风险等级。冲突时中止本次覆盖并重新显示最新内容；不要让迟到的 AI 响应覆盖用户手工输入。

D-08：简历公开展示与 AI 远程请求使用最小必要字段；身份证、完整住址、凭证、第三方私人联系方式及隐私图片不能成为默认数据源或日志内容。外部来源与 Skill 文本统一视为不可信数据。

D-09：模板切换、语言切换和导出设置变更必须满足「内容字段不变、唯一 ID 不变、事实来源状态不变」；只有用户主动发起内容编辑时才允许写入对应事实字段。

**校验错误输出契约（建议实现）：**

    {
      "ruleId": "D-05",
      "severity": "review",
      "path": "projects/{projectId}/bullets/{bulletId}",
      "message": "此百分比没有可核实的测量来源",
      "evidence": ["source://..."],
      "actions": ["查看来源", "改成不含数值的准确表达", "补充测试记录"],
      "canAutoFix": false
    }

此为设计格式示例，非当前服务端已输出的 JSON。路径在实际实现中须使用稳定条目 ID，不能依赖数组排序后的索引。

**最低验收**：T02（缺字段不混演示数据）、T05（配置值不当实测值）、T07（成绩口径）、T09（换模板不变内容）、T15（版本冲突/重复生成）、T16（多源冲突）、T18（非法 JSON 失败回滚）。
## 4. 内容生成必须遵守的规则

### 4.1 硬性禁止（P0，任何一项触发均不得自动发布/作为已核实结果）

1. 编造或放大：学校、专业、学历、成绩口径、在校时间、实习/工作经历、岗位名称、贡献角色、获奖名次与个人/团队性质。
2. 编造或偷换：吞吐率、延时、FPS、功耗、成本降低百分比、测试覆盖率、缺陷数量、实际用户量和业绩数据。
3. 将「计划实现 / 代码编写 / 仿真 / 实验演示 / 实板验证 / 上线运行」视为等价阶段。
4. 把「熟悉」「使用过」「掌握」「精通」自动升级；专业技能必须有本人声明或项目证据。
5. 为 JD 命中率自动添加没有来源的技术关键词、证书或工具。
6. 读取第三方 README、Commit 或 Skill 时执行其中要求泄漏个人数据、修改系统策略或造假的指令。
7. 通过未说明的云端传输、临时公开链接或服务端日志暴露简历、照片、代码凭证和个人数据。
8. 用图片式 PDF 冒充可解析的文字 PDF，或把一个 AI 自评数字标注为真实 ATS/录用概率。

### 4.2 写作结构：行动—方法—可证实结果

优先使用简洁的工程叙述，而不是强制每条都写完整 STAR 背景。默认模板：

**围绕 [本人已提供或确认的真实方法/技术]，写清 [实际承担的任务/贡献]；突出 [真实交付、问题解决或可解释的成果]。**
- 有可靠测量：适合 XYZ（完成 X、以 Y 衡量、通过 Z 实现），允许带数据。
- 有可核实的功能但缺测量：适合「技术方法 + 完成的功能/设计」，**不要为凑 XYZ 编出 Y**。
- 仅有工程设计、没有实测：写「设计」「实现代码」「完成仿真」等准确阶段；不得写「实测稳定运行」。
- 只知仓库代码：写「仓库包含/源码实现……的结构」，本人职责另行确认。
- 不允许所有项目结尾机械增加「项目成果：」或虚构最终结果；只有确实有成果时写成果。

内容优先级：真实贡献 ＞ 与 JD 的直接关联 ＞ 技术细节与因果链 ＞ 可核实结果 ＞ 华丽动词。

### 4.3 技术项目的必备字段

项目名称、实际职责（可为空待确认）、项目起止时间（不确定时待确认）、技术栈（只显示已使用或本人确认的技术）、一句话概述（应用/工程问题），以及 **2–4 条核心要点**（仅在材料足够时；不强制补足条数）。

每条尽量回答：做了什么？用什么方式？难点在哪里？有什么证据？它为何对应目标岗位？

技术岗位特定边界：

- 嵌入式/MCU：芯片与外设型号、GPIO/USART/I²C/SPI、任务同步、硬件调试、固件/仿真测试等，以材料实际存在为准。
- 软件研发：模块职责、依赖及 API 设计、错误处理、测试和部署，以可确认实现为准。
- 测试开发：测试设计、覆盖范围、执行方法、缺陷发现及复测，以测试报告或本人核对为准。
- 机器学习：训练/验证/测试数据划分、指标定义、样本规模、训练配置和可复现实验；禁止把训练表现说成独立测试效果。
- 硬件与电子：原理图/PCB、接口、供电、调试仪器、误差与精度口径区分设计值与测量值。

例（仅说明句式；不构成任何人的真实经历）：

已证实素材：配置 USART1 为 115200 bps，采用中断接收；未提供延时或误码测试。

合格表达：「配置 USART1 串口通信（115200 bps），通过接收中断处理输入指令，实现设备控制与状态读取。」

不合格表达：「优化串口吞吐性能 60%，实现零丢包的工业级高可靠通信。」

115200 bps 是配置参数，不等于性能提升结果。

### 4.4 用词、日期、结构

- 中文技术简历默认专业、自然、克制；避免「赋能」「深度参与」「极大提升」「业界领先」等无信息量表达。
- 同一技术名词统一写法，例如 STM32、FreeRTOS、USART、SQL Server；不为迎合 JD 擅自改变用过的芯片、库或语言。
- 日期统一为 YYYY.MM—YYYY.MM 或 YYYY.MM—至今；教育阶段、实习与项目的实际时间不得编造。
- 若成绩有多种口径，明确「GPA / 加权平均分 / 单学期 / 累计」和分母；不把单学期结果写成累计 GPA。
- 团体奖项明确团体性质，参与角色以本人确认的信息为准。
- 不因机器生成习惯把每项经历压成同样长度；允许 1 个高价值项目比其他项目占更多版面。


### 4.5 内容生成模块：岗位关联、FAB/STAR 和可信技术表达

参考 Reactive Resume 的国家/岗位/经历阶段内容选择方法，以及 ResumeSample 针对技术简历的 FAB 写法。这里的 FAB 表示 Feature（特性/实现）、Advantage（优势/技术选择）、Benefit（价值/结果）。**FAB、STAR、XYZ 都是可选组织方法，不是强制补全事实的规则。**

**内容规则 C-01 至 C-10**

C-01：生成前区分目标地区（默认国内）、目标岗位、求职阶段、用户希望突出的位置（建议 2–3 个核心卖点）。没有目标 JD 时使用通用技术简历，不因系统默认关键词假装匹配具体公司。

C-02：首先按职位筛选**已有真实内容（包含用户本人明确声明的职责与项目）**，然后再考虑表达方式。不同岗位共享相同事实源，可调整排序与重点，但不可从 JD 凭空创造经历或改写职责归属。
C-03：教育模块只展示本人已提供或资料明确记载的学校、专业、学位、时间与成绩。课程可以筛选与岗位相关的部分，但不得添加未修课程。GPA、加权分、单学期均分分别标明口径。

C-04：项目默认建议 1 句概述和最多 2–4 条要点，**不是数量下限**。只有一项有价值的工作就写一项；资料不足时保留草稿，不补「项目成果」段落。经历/科研与个人项目区分角色，不能把「仓库存在」写成「本人独立开发」。

C-05：项目要点优先按「本人确认的行动 → 实际技术实现/困难 → 有依据的结果」展开。工程细节优于华丽动词；需要量化时仅引用有上下文、单位和可靠来源的数据。

C-06：写作模式根据证据选择：有实测效果时可用 XYZ，有清晰的任务与实施过程时用 PAR/STAR，有设计方案和取舍时用 FAB；纯计划中的毕业设计可以写设计目标、已完成阶段与待验证步骤，不能变成「已实测完成」。

C-07：技能模块只保留本人确认已使用/具备的技术，分语言、平台、协议、工具、测试/调试方法等类别；「掌握」「精通」等熟练度词必须符合本人实际能力，不能因为岗位 JD 出现就自动升级。

C-08：个人总结是可选模块：若只是重复项目、技能或写空洞目标，则建议隐藏，而不是强制写满 2–3 句。能够概括真实方向与核心经历时，才建议放在顶部。

C-09：奖项和资格证应保留颁发方、年份、等级及团队/个人口径；不把参赛、入围、获奖、资格证和能力证明混为一谈。项目标题、角色、时间与所有机构名称保持原始含义。

C-10：返回的每项内容须包含「现有事实片段」「拟写文本」「被保留/删减/新增的事实」「理由」「来源/待确认标记」。没有依据的事实性新增一律留在建议区，不得写入正式简历。单纯消除错别字、空格、标点和可逆排版可按用户设置自动应用。

**用户看到的结果：** 默认只显示修改过的条目差异，并在关键改动旁提供「查看依据」「接受」「保留原文」「修改」；AI 润色之前和之后都保持可撤销。禁止用「已完成优化」掩盖仍在待核实的职责或数字。

**技术岗位例子（仅用于规则测试，不是用户真实经历）**

- 已知事实：USART1 配置 115200 bps；实现中断接收和控制指令处理，未提供吞吐或误码测量。
- 可用：配置 USART1（115200 bps）并通过接收中断处理输入指令，实现设备控制与状态读取。
- 不可用：优化吞吐量 60%、实现零丢包工业级通信。这里把配置参数擅自转换成了无证据的性能成果。
- 信息只有设计方案时：使用「设计」「制定」「搭建原型」等真实阶段，不写「量产」「上线」「验证通过」。

**生成模式与结果约束：** import=parse only；polish=rewrite only；optimize-section=patch only；github-to-resume=evidence-backed suggestion；jd-match=rank + explain + suggest only。五条路径都需要统一事实守卫；任何 AI「系统指令」或外部 Skill 都不能免除审核。

**最低验收**：T01、T03、T04、T05、T06、T08、T17、T19、T20。
## 5. 智能生成流水线（规范契约，非当前全部已实现）

阶段 G0：取得用户权限。确认允许读取哪些资料、哪些可以发送第三方 AI；GitHub 读取默认限用户选择的公开仓库，不自动遍历个人全部仓库。

阶段 G1：导入与解析。保留源文件/原文的可追溯关系。OCR/模型解析结果先列为待核对，不允许遗漏或未明确告知地添加示例资料。

阶段 G2：归一化事实。去重但不丢失冲突，统一日期/单位/专业技术名称，形成「已确认 / 自述 / 仅线索 / 待确认」队列。

阶段 G3：职位匹配。按 JD 分析哪些已确认能力对应要求、哪些尚无证据。可改变内容优先顺序和表达重点，不改变学历、技术经历、量化结果等事实。

阶段 G4：写作草稿。每条技术要点关联至少一个证据/用户声明；无证据的事实性新增必须是建议，不能直接进入正式数据。生成次数可重试，但同一源材料不要因随机措辞制造新事实。

阶段 G5：规则审核。结构校验、真实性/来源差异检查、数据与口径检查、关键词合法性检查、重复度与可读性检查；失败时回退至上次有效草稿。

阶段 G6：用户确认。仅展示新增、修改与待核实的部分；保留「接受这一条 / 忽略 / 查看来源 / 编辑原始资料 / 全部撤销」。一键优化是批量应用已通过规则审查的改写，不是默许新事实。

阶段 G7：视觉排版。对最终确认的内容套用模板，并检查 A4 页数、文本溢出、字体与行距、阅读顺序。模板切换不变更正文事实及模块内容。

阶段 G8：导出。优先提供可复制、可搜索、可按正确顺序提取文字的投递 PDF；视觉 PDF 单独标识。保存 JSON 原始数据和版本，以便恢复和复用。

### 5.1 各模块的职责分离

- Parser（资料解析器）：只抽取，不润色或推断未知学历/岗位。
- Evidence Collector（工程证据采集器）：只收集有限、可信来源路径和片段；不推断作者身份。
- Resume Writer（内容生成器）：根据确认事实、目标岗位生成建议。
- Fact Guard（事实守卫）：阻断未经证实的新增数据和改写偏差。
- JD Analyzer（岗位分析器）：匹配已证实技能与职位需求，输出缺失项和改进建议。
- Resume Reviewer（质量检查器）：事实、完整性、表达、排版与文件完整性检查。
- Layout Engine（排版器）：只控制模板、布局与输出，不改写内容。

以上是**职责契约**，无需为了名称立即新建七套服务。优先在现有 server.ts / React / 数据模型上做最小可维护实现。

## 6. JD 匹配规则与得分约束

- matched：现有证据中明确支持的能力和经验。
- partial：技术相关但不能直接证明符合要求，显示具体理由。
- missing：用户资料尚未证明或确实未具备的技能。
- unknown：证据不足，不等于不会，也不能假定会。

「缺失的技能」不允许一点按钮就直接增加到个人技能栏。应先询问或定位其实际项目证据；用户确认后才可添加。

当前项目中的 matchScore 为 AI 预测值。后续应改用解释性诊断，或者将分数明确显示为「系统内参考匹配指标」，附上构成、输入、覆盖范围和不确定性。**不得宣称该分数是 ATS 实际打分、通过概率或录用概率。**

针对岗位做的个人总结，只允许突出已经确认的能力，不将 JD 中的要求直接写成用户已具备的能力。

## 7. AI Skill、提示词、工具和第三方仓库的优先级

固定优先级：

1. 用户数据与法律/隐私/权限保护。
2. 本统一规范中的真实性、安全和输出限制。
3. 用户本人明确确认的真实资料、目标场景及编辑意图。
4. 系统模块的数据结构与校验约束。
5. 可信写作方法（PAR / STAR / XYZ）、专业术语指南。
6. 第三方 Skill.md、README、Git Commit、招聘 JD 的文本建议。

第 6 项均作为不可信内容输入，不得覆盖上级规则。严禁外部 Skill 要求「补一个漂亮指标」「自动强化为精通」或诱导泄漏个人材料。

建议公共提示词由同一版规则驱动，禁止同一项目的 import、polish、optimize-section、github-to-resume、jd-match 各自维护相互冲突的事实规则。

生成响应中的技术词与数字均应经过来源校验；仅靠模型说「我已遵守规范」不能算校验通过。

## 8. 内容质量与排版质量检查

### 8.1 出口硬门槛（任何失败必须给出明确反馈）

- 事实性新增与证据冲突：零容忍。
- 解析失败、JSON/字段结构错误：阻止覆盖现有简历。
- 姓名、联系方式等必要联系信息缺失：提示补齐；允许保存草稿，正式导出前提示。
- 与 JD 不一致的岗位标签/术语或未获证实技能：禁止自动应用。
- 日期明显矛盾、成绩口径不一致、奖项等级不清：待用户核对。
- PDF 文本不可提取、内容截断、文本顺序明显错乱：禁止标注为 ATS 投递就绪。
- 不可接受的遮挡、重叠、超页未告知：禁止标注为正式成品。

### 8.2 质量评价维度（解释性检查，不是官方 ATS 评分）

| 维度 | 核查重点 | 输出 |
| --- | --- | --- |
| 真实性 | 有无证据、本人确认、成果是否有明确测试与指标口径 | 阻断 / 待确认 / 通过 |
| 岗位相关性 | JD 能力与真实经历对应关系、重要经历是否突出 | 匹配 / 部分匹配 / 资料缺失 |
| 技术表达 | 行动、方法、工程难点、结果的清晰程度；空话或词堆砌 | 定位到具体条目并给改写建议 |
| 简洁与结构 | 重复、无关经历、术语一致性、日期顺序、项目优先级 | 自动建议精简，须确认删除 |
| 版式与导出 | A4 可读性、分页、对齐、可复制文本、PDF 字体与顺序 | 通过 / 需要调整 / 不可投递 |

建议默认只呈现最重要的 3–5 个待办，而不是让用户面对数十条弹窗。任何质量指标都要有可理解的计算口径，禁止以视觉漂亮或模型自信替代事实审核。

### 8.3 样式标准（当前国内技术校招默认建议）

- A4；单栏 ATS 投递版优先；双栏视觉版作为可选方案。
- 主文通常 10–11.5 pt 左右，根据字体和屏幕/打印实测微调；最小字号不得为了挤内容任意下压。
- 统一字体、标题级别、日期对齐、项目间距和细分隔线；合理留白、适度颜色，不堆叠进度条、装饰性图标。
- 联系方式清晰，GitHub 可用可点击链接，链接文本易阅读。
- ATS 投递版优先文本层，不将整页栅格化为图片；实际兼容性取决于招聘系统，不能保证所有 ATS 识别。
- 视觉版与 ATS 版共享同一份简历事实数据，只改变样式和导出路径。


### 8.4 视觉排版模块：可读性、模板契约与导出

借鉴 Awesome-CV 用命名结构定义 header、section、entry、date、description 的思路，以及 RenderCV 将字体、页面、颜色、间距做成可配置设计令牌的方法。CraftCV 的 React 模板不直接复制其 LaTeX / Typst 排版代码。

**排版规则 L-01 至 L-10**

L-01：模板接收同一个 ResumeContent + ResumeStyle + ResumeLocale，不在组件内部编造、拼接、删掉或改变事实；允许用户选择隐藏模块，但隐藏不是删除源数据。

L-02：版式结构至少明确姓名/目标标题/联系方式、一级章节、条目标题/机构、日期/地点、正文要点。信息层级一致；不靠大量不同字号或色彩表示「优秀」。

L-03：按投递地区选纸张：国内默认 A4，国外按照目标机构要求决定 Letter/A4。单栏 ATS 投递优先，但双栏视觉版可保留；不得把「单栏」等同于百分百通过任何 ATS。

L-04：字号、行距、页边距应使用统一令牌。国内技术简历正文可从约 10–11.5 pt 开始试排，实际以字体、中文密度和打印效果为准；这不是固定限制。设计系统应给出可访问的最小可读字号范围，超页先调整内容或转多页。

L-05：页内避免标题孤行、经历条目被不合理拆散、正文与照片/浮层重叠、页脚被截断；不能使用不可见隐藏文本、白色关键词堆砌、过度压缩字间距骗过筛选系统。

L-06：同一份简历在 12 款模板之间切换后，内容、ID、来源状态及条目顺序必须不变，除非用户明确手工拖拽/修改；模板色彩、日期位置和排列可以不同。

L-07：点击可见文字优先进入对应字段的编辑状态，点击模块空白区进入表单；拖拽手柄/模块用于调序，不能因单击文字而误触发移动。键盘 Enter/取消、失焦与长文本输入需可预测。

L-08：插入图片和照片时取得许可，确保清晰、比例正确和可关闭。照片、装饰、侧栏不应使 ATS 文本顺序错乱；联系方式文字应可被复制，不只依赖图标。

L-09：投递 PDF 必须带可提取文本层，并以实际导出后的 PDF 为准验证中文字符、阅读顺序、链接、页数、空白尾页、页面裁切、字体缺字。视觉截图 PDF 必须明确标注为非文本投递版。

L-10：导出界面准确告知哪一个按钮「直接下载图片式 PDF」、哪一个是「浏览器另存文字 PDF」。不得声称文本 PDF 的版式与预览 100% 一致，或保证所有招聘系统都能解析。

**默认的检查方式：** 选择至少三个风格差异明显的模板，加上内容特别长、包含中英文符号和无照片的样本；实际渲染、打印/导出、读取 PDF 文本并检查首尾内容与分页。在实机中复核 Chrome/Edge、Windows 缩放及常见窗口宽度。与原编辑器交互有关的测试还应验证拖动、撤销与刷新后恢复。

**最低验收**：T09、T11、T12、T15。新增模板还应通过切换不丢字段、可点击修改、拖拽调序和至少一条真实导出回归。

### 8.5 成品质量审核模块：硬门槛、待确认与建议

参考 Reactive Resume 将内容审查、国家场景和 ATS 检查分别处理的方式。CraftCV 应使用**确定性规则优先、AI 审阅辅助**的体系。AI 可以提出可能问题，但不能凭自身评价为候选人打出「实际录用概率」。

**审核状态与决策表**

| 状态 | 典型触发条件 | 对保存/导出的影响 | 用户动作 |
| --- | --- | --- | --- |
| BLOCKED（事实/安全阻断） | 非法数据覆盖、无授权远端传输、确定的敏感信息泄漏、未经审核自动新增技能/成绩 | 阻止危险的自动应用；仍可保存/导出带明确「草稿」标签的用户自有内容 | 查看来源、撤销建议、修复或授权 |
| REVIEW_REQUIRED（待确认） | 成绩口径冲突、身份与个人贡献尚未确认、实测数据只有自述、日期不全 | 允许保存草稿；正式版显示明确提示，用户确认后可继续 | 补证据、核实、标记为用户自述、调整说法 |
| NEEDS_LAYOUT（版式需要调整） | 末页空白、正文裁切、缺字、文本读取失败、严重遮挡 | 不显示「投递就绪」；提示换模板、改版或多页 | 修复版式后重新导出并复查 |
| SUGGESTION（可选优化） | 措辞重复、次要内容过长、章节排序不够贴合 JD | 不阻断正常保存与正式导出 | 选择性一键优化或忽略 |
| READY（通过当前检查） | 当前所启用的校验项目通过，必要问题已处理或标记 | 允许标注「通过本项目当前检查」 | 下载与备份；不宣传必然通过招聘筛选 |

注意：未经人工核实的用户自述，可以如实进入简历，但不能被标注为「第三方已认证」。系统要区分「用户自主承担的自述」与「AI 无提示编造」；不能要求普通求职者为每句话提供正式证明才能使用软件。

**审核规则 Q-01 至 Q-10**

Q-01：结构检查（确定性）：必填联系信息、字段类型、ID 唯一性、非法 JSON、数组结构、链接协议、日期明显矛盾、不可访问的模板 ID。

Q-02：来源检查（事实守卫）：对照修改前后的原始事实，重点检查学校/专业/学历、任职机构和时间、技术栈、个人职责、成绩、奖励等级与量化指标。有新增但无依据时默认阻断自动应用。

Q-03：量化检查（规则 + 人工复核）：提取百分比、时间、精度、QPS、功耗等数字，辨别配置参数、实验测量、公开仓库声明和用户估算；不自动把没有对照基准的数据解释为「提升」。

Q-04：JD 审核（非概率）：输出 matched / partial / missing / unknown，加上支持该结论的条目和来源；未知并不代表不会，不能因为 JD 缺词就将其添加到技能。

Q-05：表达审核：检查空泛形容词、重复动词、责任范围夸大、非技术性的堆词，提出具体可核实的替代写法；保留用户原稿供对照。

Q-06：情景审核：国内/海外、校招/社招、技术岗位/学术 CV 分别核查页数、照片、敏感字段和内容排序；有岗位明确要求时先遵循岗位要求与法律权限边界。

Q-07：版式审核：渲染 A4 或 Letter 的实际页面，检查段落截断、页码、空白尾页、可复制文本、符号/中文缺字、阅读顺序及超页提示。

Q-08：问题排序：默认展示影响投递的前 3–5 项，所有问题可查看完整列表，按路径跳转至编辑字段；同一根因合并，不重复弹出十余个通知。

Q-09：质量评价必须透明。可以展示各维度「通过/待核实/待调整」，任何分数应声明为内部自定义指标、展示构成与不确定性；不使用「ATS 官方得分」「录用成功率」等不成立的名称。

Q-10：修改与回归：自动修正仅适用于排版、错字、规范化格式等不改变事实的内容；实质改写需要审批。每次正式导出后对导出文件再验收一次，失败时保留原版与调试证据。

## 9. 对用户的数据控制与错误处理

- 用户原始简历、上传文件、已经确认的经历不能因 AI 生成失败而被清空或覆盖。
- 自动生成只提出修改建议；在确认前保留原稿、差异预览和一键撤销。
- 只在用户允许的范围内对接第三方 AI；对每次云端发送明确说明会发送什么（简历、JD、源码片段等），并限制发送内容和日志暴露。
- 读取 GitHub 时使用公开 API，限制文件数、文件大小和超时；不扫描环境变量、凭证目录或个人隐私文件。
- 缺少网络/模型权限时仍可手动编辑、导入现有 JSON、使用模板、导出，不以付费或外部服务作为必要前提。
- 对并发导入和重复生成采用版本校验与幂等处理，避免较晚完成的旧请求覆盖用户最近编辑。

### 11.9 ATS 分页与页间留白回归（2026-11-08）

**目标与根因。** 原有 Chromium ATS 打印在长项目上统一采用 `break-inside: avoid-page`，会把项目整体推向下一页，造成大量未使用纸张空间。旧版 `max-w-[280px]` 项目链接在单栏仍分成两行；同时 `@page 12mm` 与视觉模板自带的 `px/py` 内边距叠加，导致打印实际留白与规范不符。经典 ATS 的 `section` 也曾缺少用于分页保护的类型标记。

**实现（只影响独立 ATS 打印版）：**

- `src/index.css` 为纸张只保留一层 A4 12mm 物理边距；打印与屏幕隐藏预检版都移除原视觉模板额外的 `padding`。照片/双栏视觉模板和原高清截图 PDF 仍保留已有设计与尺寸。
- 项目 GitHub 长地址使用 ATS 单栏实际宽度，不再被视觉模板的 280px 容器限制；正文 URL 文本及超链接数据未改变。
- `src/utils/atsPagination.ts` 使用保守、可测试的内容长度启发式：**不超过 350 字符且有效要点不超过 4 条**的项目优先整块留在同页；较长项目允许在完整项目要点之间跨页，单条要点尽量不断开。Chromium 仍负责最终分页，启发式不能保证每份复杂简历恰好无孤行；过长单个要点由浏览器安全回退。
- 经典 ATS 模块显式暴露 `data-resume-section` 和 `data-ats-section-heading`，将防孤立规则绑定到真正可见的模块标题，而不是可能存在的隐藏拖拽控件。个人简介/教育/奖项/经历等短模块优先保持完整。不改变 ResumeDocument/SectionConfig/简历内容，原有 0–40px 全局和各模块间距继续生效。
- `tests/verify_ats_pdf.py` 增加可选 `--max-intermediate-blank-mm 30`：只在文件级 QA 时拒绝中间页（非末页）底部超过指定阈值的空白，并输出每页剩余空间。阈值是对比测试的质量门槛，不是所有简历的一般性硬性限制。

**真实验收（匿名演示简历，Windows Chrome，固定全局 28px、项目独立 38px）：** 旧版两页 A4 第一页最后文字后约 **69.0mm** 未使用空间；本版通过实际 Chrome 打印与 PyMuPDF 文件读取，第一页降至 **28.8mm**，第二页从完整项目名称开始，不再以孤立的项目成果要点开头。新旧 PDF 除空白和换行外的文字完全一致（归一化后 2014 个字符）；页数仍为 2，中文文字层、Arial 与微软雅黑的字体子集嵌入、A4 尺寸和页面越界检查通过。旧版在新 30mm 留白门槛下失败，新版通过。渲染图、最终 PDF 与检查报告保留在忽略提交的 `_private/pagination-qa/`。

**适用边界：** 当前实测只覆盖该匿名演示数据、Windows Chrome 和选定的间距参数。自定义长项目、长链接、其它字体/浏览器和真实招聘平台 ATS 尚未全量验证；打印前的页数预检是近似值，实际 PDF 页数与文字完整性以导出文件为准。启发式不等于引入新的独立分页引擎，也不自动改写用户内容。

### 11.10 模块内部精细排版（2026-11-08）

**目标与数据契约**：在现有顶层模块间距及 P0 ATS 分页之外，让个人简历可独立调节 **项目/实习条目之间 0–28px**、**模块标题与正文之间 0–20px**、**项目/实习要点之间 0–12px**。三个字段位于 `ResumeStyleConfig`：`itemSpacingPx?`、`headingContentSpacingPx?`、`bulletSpacingPx?`。所有字段可选，未定义或非法类型使用原有模板排版，不向旧 JSON 自动写入新的值；显式 `0` 视为有效覆盖值；有限数值经 `normalizedInternalSpacing` 保守取整与限制，不向 CSS 传递非法数据。

### 11.11 正式导出前质量预检（2026-11-08）

**目标**：将原 ATS 按钮上分散的 `window.alert/window.confirm` 和图片按钮的直接下载统一为导出前审阅流程；不把“浏览器预检”冒充“已检验生成的 PDF”，不因无凭证/其他模板不同而改变用户真实数据。

**真实实现范围**：`src/utils/exportQualityPreflight.ts` 以当前实际隐藏导出画布的几何尺寸生成带等级、原因和修改建议的 `ExportQualityReport`：可测量性、保守预估 A4 页数、横向溢出、姓名及求职方向空白、电话/邮箱均缺失、无可见模块、字体仍加载以及多页分页风险。ATS 使用已有 `inspectAtsPrintGeometry`（186mm 内容宽、每页 12mm 边距），图片版使用 210×297 比例与当前截图画布；两个格式分别说明文本层能力。明确错误（画布未就绪、尺寸无效、横向越界）阻止继续，普通多页/信息缺失使用警告而非强制禁止。每个问题展示可操作建议，允许「返回修改」、确认继续、Esc 关闭，弹窗的 Tab 焦点循环限定在按钮间。

**该阶段发现的缺陷（已在 §11.12 修复，以下保留历史验证结论）**：独立检查高清版输出图片发现 **经典工程双栏 `pdf-classic` 的项目标题/日期/正文局部重叠**。Chrome DOM 中对应元素的几何框并无重叠，字体等待也未消除此问题，归因倾向于截图序列化/渲染阶段但未完全确认；尝试现有间接依赖的另一渲染器未得到稳定验收，因此本轮不更换正式截图引擎、不增加新依赖。对此模板在 `ExportQualityDialog` 明确展示可复现的排版风险警告和“发现重叠勿用于投递”的操作建议，**不声称图片 PDF 已通过视觉验收**。后续应单独修复截图引擎的版式保真，并逐个模板完成高清 PDF 的实机比较；本轮的 ATS PDF 验证仍保持独立有效。

### 11.13 高清图片 PDF 按内容边界分页（2026-11-08）

**问题与修复**：§11.12 之后，图片导出仍把一张长 JPEG 以 297mm 为步长直接平移到后续页面；文件尺寸正确，却会在页末截断一行中文、拆开项目标题/日期，甚至造成“模块标题留在第一页、正文从第二页开始”。本阶段保持 `html2canvas-pro@2.6.3` 三倍截图、原有 12 种模板和用户字号/模块间距，不再复用整张长 JPEG 的负偏移分页。

**单一分页权威**：新增 `src/utils/imagePdfPagination.ts`，从隐藏导出画布中读取真正参与渲染的文字行 `Range.getClientRects()`、图片和 SVG 元素的纵向占用区间，忽略 `.no-print` 工具；另外保护 `[data-cv-section-heading]` 到其正文首行、项目标题到首条 bullet 的整段区间，避免孤立标题及首条要点拆散。纯函数 `planImagePdfSlices` 将该区间归并，在 A4 最大像素高度内选择安全断点，并优先靠近真实条目边界。每页的 `start/end` 区间严格连续、无像素丢失和重复；正常页保留原 3 倍图片比例，只有最终纸张溢出少于 1% 时允许轻微适配。画布内容过密且无法安全断页、尺寸非法或超过 40 页时，不伪造成功，不回退旧硬切逻辑，直接提示调整模块或使用 ATS 文字 PDF。

**真实 PDF 输出**：`src/App.tsx` 保持原 jsPDF/A4/高清 JPEG/下载文件名与两阶段确认机制，在单张截图结束后依据真实 DOM 位置算出所有切片；使用白底 A4 页 Canvas 对源图按区间逐页裁剪，然后独立写入 PDF，剩余页脚留白而非拉伸正文。不会为分页而删减文字、修改简历数据、覆盖单模块间距，ATS 文字打印仍完全独立。

**回归证据与边界**：新增 `tests/imagePdfPagination.test.mjs` 覆盖单页、跨页连续性、临界线、双栏重合区、安全失败、标题/首段绑定及源代码中旧 JPEG 平移路径移除；更新图片质量和导出前预检断言。Windows Chrome 通过实际「更换模板→一键高清 PDF→检查→确认→下载」逐项对 12 款匿名演示模板生成真实 PDF：**12/12 A4 文件及非空图片层通过**，经典双栏 1 页，其余 11 款在此示例下为 2 页；逐页截图核对了页底/页首接缝，经典 ATS 和创意分栏原先孤立的模块标题已移动到下一页与正文同行，不再复现旧的字行硬切。保留 `_private/image-pagination-qa/template-pdfs/`、`final-seams-{1,2,3}.png` 与 `final-image-pagination-report.json` 作为可复核证据。**限制**：这些证明基于 Windows Chrome、匿名演示简历和目前 12 款模板，不保证极长用户自定义表格、远程字体或任意复杂内容必然存在安全断点；对于不可安全分页的文档，系统会拒绝图片版输出并建议 ATS。图片 PDF 仍不可复制正文文本，正式投递仍需检查目标平台要求。

### 11.14 校招「严格单页」与非破坏性一页适配（2026-11-08）

**产品定义**：一页 A4 是本科/应届生校招简历的优先目标，**不是对所有岗位的一刀切规定**。简历保留两种可切换的页数目标：`style.pageGoal: 'one'` 表示「严格单页」，`'flexible'` 或旧数据省略该字段表示「允许多页」。目标保存在当前简历版本中，按版本管理、撤销和 JSON 备份自然兼容；旧版本默认不会被突然禁止导出。用户可在「模板与版式→校招简历页数目标」或编辑器预览顶部直接切换。

**安全排版**：曾有的「一键收敛一页」把正文字号强行设为 `sm`（11.2px），却没有验证实际输出。这一做法已改为 `src/utils/onePageResume.ts` 的单一 `compactOnePageStyle`：只将既有 `lg` 调回 `md`、采用紧凑但可读的行高和页边距、缩小全局非个别覆盖的模块上方间距，**不会将标准字号自动变成小号**；不覆盖 `section.spacingBeforePx`、细粒度 bullet/标题间距、个人事实、技能和项目条目。所有排版更改可撤销，触发该操作会明确打开严格单页目标，但“尝试”不代表已经成功。

**实际约束**：`buildExportQualityReport` 在单页模式下，对**各自独立**的视觉画布和 ATS 打印画布估算 A4 页数；超过一页时显示 `single-page-limit` 错误和修正建议，禁用继续导出。视觉图片版即便预检认为一页，也会在 `html2canvas-pro` 完成截图并按真实源图计算 `planImagePdfSlices` 后再次判定；若结果多于一页，则抛出 `SinglePageLimitError` 并拒绝保存，不截断第二页、不全局缩小、不偷偷切换到 ATS。切回允许多页后仍使用 §11.13 的内容安全分页。ATS 打印来自 Chrome/Edge 原生打印对话框，本工具**无法读取用户另存后的 PDF 并强制保证其页数**，因此一页预检通过仍明确提醒检查真实文件，绝不声称浏览器估计等于最终页数。

**实机与测试**：新增 `tests/onePageResume.test.mjs`，扩展导出预检、简历 JSON 恢复和图片导出回归。Windows Chrome 按真实用户操作路径逐一检查：现代极简模板在严格单页下，高清 PDF/ATS 两种导出前检查都检测到两页并禁用继续；经典工程双栏在同一严格目标下允许导出，实际 PDF 经 PyMuPDF 证实只有一页；重新设为「允许多页」后，现代极简恢复可导出。所有验证均采用匿名演示简历；不代表真实用户的每份简历能无损收缩为一页。保留 `_private/campus-one-page-qa/` 下的浏览器截图、实际单页 PDF 和 JSON 验收报告。

### 11.15 AI 一页精简草稿与无 AI 排版/模型配置分支（2026-11-08）

**用户触发与边界**：当简历超过一页时，可在预览顶部点击「AI 精简方案」，或在「模板与版式」选择「AI 一页精简建议」。一个点击只触发这一轮 AI 方案生成，不直接改动现有简历；弹窗先调用 `GET /api/ai/models` 判断是否有当前服务器真正配置的模型。**没有模型时绝不 POST 任何简历内容到 AI**，弹窗只提供「确认压缩间距」和「查看 AI 模型配置说明」：前者预先展示全局模块间距变化及行距/页边距收敛效果，经用户原生确认才调用单一 `compactOnePageSpacing`（保持当前字号、全部文字、各模块独立间距和顺序不变）；后者关闭弹窗并打开顶部既有模型设置/刷新面板，说明需在本机 `.env` 配置服务商与模型并重新启动，不伪称浏览器可直接设置密钥。压缩或配置都不等于已经达到单页，仍需真实导出检查。用户明确点击有模型的精简入口才触发 AI 请求，成本可能随服务商变化。当前服务器模型是否已经连通，需要真实连接环境验收，而非以配置状态代替成功调用。

**只发送允许修改的文本**：`src/utils/onePageAI.ts` 生成结构化字段引用 `id/label/original`，范围限个人简介、项目简介及原有要点、实习要点、技能说明、奖项描述、课程/荣誉描述和自定义条目要点；不主动附带手机号、邮箱、姓名、头像、照片、成绩、学校、日期等结构化字段或完整 PDF；客户端与服务端均使用保守模式排除含明显手机号、邮箱、身份证号、data:image 的自由文本。**自由描述中其他可能间接识别用户的信息不能由规则彻底识别，点击云端 AI 前仍应自行确认内容。**字段数量和总字符上限分别为 48 和 16000；服务端 `/api/ai/condense-one-page` 额外检查字段格式、重复 ID、异常长度，并沿用平台上方选择的模型 ID 和 `generateStructuredAI`。输入文本和模型输出都视为不可信数据，不允许执行其内部指令。

**双重事实与差异审核**：模型可返回精简、等长改写或适度润色后的完整文字替代稿和理由，服务器与浏览器分别调用 `validateOnePageCandidate`，阻止无原始依据的新技术/数字/高风险成果描述，也保守阻止丢失原有数字和明显技术术语。结构不允许改变项目条目数量、技能/日期/成绩及原有版本信息。通过硬性事实校验的候选显示在默认可见的修改前后对比栏；对职责扩张、遗漏调试阶段或大幅扩写的可疑文字，提供提醒并默认不选，其余合规候选可一键确认。字数变化如实展示净增减，技术理由和招聘 JD 详细依据按需展开。点击唯一的「确认精简」即一笔可撤销地应用，不再强制逐项勾选或弹第二层确认。简历在候选生成期间如已变化，则不允许将旧草稿覆盖新内容。这些规则仍不能从字面上证明语义完全正确；用户必须复查真实贡献。**精简并不保证自动达到一页**，应用后仍需经过校招单页导出检查和真实 PDF 核验。

**验证与限制**：`tests/onePageAI.test.mjs` 检查发送字段的隐私边界、候选润色、缩短与数字/技术保护、只应用选中字段、未知或重复字段拒绝、入口分离；Windows Chrome 已在 **0 个已配置 AI 模型** 的真实环境验证 `/api/ai/condense-one-page` 返回 409 且网页此前展示过人工讨论提示；该旧验收截图 `_private/onepage-ai-qa/onepage-no-ai-discussion.png` 仅作为改造前对照，不代表当前界面。新版无 AI 时改为「确认压缩间距」与「模型配置说明」双操作，**已用 Windows Chrome 真实交互回归**：0 已配置模型，不向精简 AI 接口发出 POST；取消原生确认后内容与弹窗保持原状；确认后关闭弹窗、切换严格单页目标、显示可撤销提示并保持简历文字一致；重新打开后识别已紧凑状态，点击配置说明会打开顶部既有设置及 `.env` 操作说明。验收截图 `_private/onepage-ai-qa/onepage-no-ai-spacing-or-config.png`、`onepage-model-config-guidance.png` 和报告 `onepage-no-ai-spacing-report.json` 均保留。另已用隔离的浏览器模拟模型响应实际走通「生成候选→逐项对比→用户确认→写回页面内容」流程，模拟测试报告在 `_private/onepage-ai-qa/onepage-mock-integration-report.json`，不涉及任何真实 AI 请求。在没有 API 凭证的环境中**无法对真实外部 AI 生成质量做端到端验收**；后续应在获得用户授权的模型账户下检查计费、模型响应、隐私和事实校验行为。原有 `AIOptimizeModal` 的逐项润色入口继续保留，不被新全简历工作流覆盖。

### 11.16 岗位导向精简与原文证据可追溯（2026-11-08）

**目标**：对同一份应届生简历，优先提升目标岗位的信息密度，而非为凑一页任意删减描述。保留 §11.15 的无 AI「确认压缩间距 / 配置 AI」双入口，也保留每次编辑前的逐项确认与撤销。当前引擎**不自动删除项目/经历/技能条目，也不伪造硬件实测或个人贡献**。

**岗位上下文**：首次点击 AI 精简时，沿用简历中的「目标岗位方向」作为低成本一键初评；若提供真实招聘 JD，可以在同一对话框粘贴不超过 3000 字的岗位要求并主动点击「按当前岗位要求重新分析」。无 JD 的初评必须显示「仅依据岗位方向推断，不是企业招聘匹配」；有 JD 时每条修改必须带 `jobBasis`，且该片段能在用户给的 JD 原文中逐字查到。每次重新分析都是新模型调用，可能产生额外费用；仅修改输入框不能偷偷再次调用 AI，并会禁用旧候选的应用按钮。岗位文本也是不可信数据，不能当成模型指令。

**证据契约**：后端 `/api/ai/condense-one-page` 要求每条候选输出 `relevance: high|medium|low`（AI 编辑推断，非 ATS 分数）、`evidenceQuote`（源字段确切片段）、`jobBasis`（若给出 JD 则必须逐字来自 JD）、`reason`（具体岗位与写作原因）和 `tradeoff`（可能丢失的工程含义）。另输出最多 6 条 `keep` 保留建议，均需匹配原文确切引文。服务端和客户端共同调用 `validateOnePageJobSuggestion / validateOnePageKeepRecommendation` 拒绝无来源引文、伪 JD 依据、未知相关性及丢失数字/明显技术术语的内容，保留建议不会改变任何原文。字段仍受 §11.15 的隐私筛选和长度限制；岗位名称及 JD 不得含明显手机号、邮箱、身份证号等联系信息。

### 11.18 宽松专业润色与事实底线（2026-11-08）

根据用户反馈「不要太过严格，有时需要适当美化与包装」，AI 一键精简采用 **专业表达优先、事实边界兜底**，不再机械要求每条候选必须比原文更短。允许重组句式、突出原有的技术难点和贡献、适度增加文字来提高说明力；后台仍用最终 A4 排版检查页数。候选须与原文有实际差异，不得新增无依据的数字、技术、完成状态或夸大岗位责任。

**确定性硬保护**：`validateOnePageCandidate` 对新增数字/性能提升、无依据技术词、丢失原有数字及明显技术词、虚构主导与独立负责、将待验证项目改写为验证通过或稳定上线等行为拒绝。校验针对当前字段原文，不把外部仓库能力自动当作个人贡献；规则只能发现常见风险，不能证明陈述的技术含义完全一致。

**非阻断的审阅提醒**：`getOnePageWritingWarnings` 对「参与/协助 → 负责」、遗漏「调试中/待验证」状态以及明显大幅扩写产生提醒，**不直接丢弃该建议**；这些项展示在默认可见的红删/蓝增对比里，但默认不勾选，候选人明确勾选后仍可一次确认。一般专业润色继续默认勾选，一键确认不新增额外弹窗。没有来源台账的普通简历文字不因此被一概拦截；标明 AI 推断而非第三方核验，实际贡献仍需本人审查。

**透明字数与质量取舍**：每条候选如实标注「减少 N 字 / 增加 N 字 · 表达润色 / 等长专业改写」；整体显示**净增减**而非只累加减少的文字。短句优先保留技术证据，准确表达优先于机械缩字；与严格单页的冲突留给实际 A4 测量、用户修改及既有 PDF 导出守卫处理。无 AI 分支仍是「确认压缩间距 / 配置 AI」，不会调用任何 AI 请求。

### 11.21 共享母版证据与上传即识别（2026-11-08）

依据用户新决定，统一资料入口为「母版资料」：跨所有岗位简历版本共享附件原件、来源摘录和 OCR 候选事实，而不是每个岗位重复上传。选择文件即对兼容的当前模型发起一次识别，不再要求额外的授权复选框；上传前须明确显示当前模型、云端传输、费用与隐私风险。无法识别时保留文件和可重试状态，不宣称成功。

同一内容按 SHA-256 计算字节级指纹，重复文件（即使重命名或来自旧版岗位槽位）只复用本地已识别结果。IndexedDB v1 → v2 非破坏性升级、原有分槽记录原地保留、不迁移多份 Blob；统一查询历史与新增母版资料。确认删除前告知会从所有岗位版本移除，旧来源不因自动识别被升级为 verified。上传照片/成绩单不等于允许将未经核对的学历、分数或个人贡献自动写进正式简历。母版可作为后续事实审核来源，但其他 AI 文案接口尚未自动调用母版数据。

验收：静态类型、全量测试、生产构建；匿名 Chrome 真实 UI 经模拟模型响应验证上传触发且未出现授权框、同字节改名重复不二次调用、刷新恢复和删除确认。真实云端识别精度与费用未验证，图片/PDF 能力取决于所选模型。具体流程与隐私说明见 docs/EVIDENCE_ATTACHMENTS.md。

### 11.22 母版证据自动分级与异常优先（2026-11-08）

在 11.21 的一次上传、一次识别与跨版本母版缓存上，新增**浏览器本地**确定性事实审查。每条候选依次检查必要归属、识别值与模型来源摘录的字面对应、对同一机构且可安全关联的现有简历字段的差异、母版其他同字段候选值。无异常自动归档为来源候选并默认折叠，来自不同文件指纹的同字段一致标为「多材料一致」，冲突/缺失/引用不对应的内容才自动展开提醒；单独保留模型识别备注。没有二次 AI 调用或逐字段确认流程，刷新/岗位切换后根据母版与当前简历重新计算，不新增缓存副本或昂贵重复调用。

禁止将「AI 结构完整」「原文摘录字面匹配」「多份字节不同材料一致」描述为证件真伪认证、第三方验证、本人贡献证明，或据此在未审阅时自动覆盖正式简历。GPA 与加权成绩、不同课程分数、赛事年度/证书颁发时间、团体/个人奖项应分别建组；字段/机构无法可靠关联时保持保守，不制造虚假冲突。自动归档是来源候选记录的整理，不是正式投递内容的事实确认。

新增纯函数及约 14 项单测、匿名 Chrome UI 验收：正常内容默认折叠、异常自动展开、重命名重复不再发送、刷新后从母版重新推导异常。真实视觉模型 OCR 准确率、人工复核后的正式事实账本写回、官方来源验证均不在本轮范围。详细说明见 docs/EVIDENCE_ATTACHMENTS.md。

### 11.23 结构化母版检索增强（2026-11-08）

当前资料规模优先使用可复核的本地结构化检索，而不引入 embedding/向量库。JD 诊断和单项 AI 优化在用户主动使用时先读取母版来源候选，调用原有自动核验规则过滤已知冲突，以岗位/条目相关性挑选最多 10 条教育、奖项和证书候选。新增唯一来源编号、目标字段、原文摘录、候选值及一致性级别，服务端对 JSON 输入再次做字段白名单、长度限制和常见敏感信息排除；不传原件或整个母版，不在后台自行读取或额外调用模型。生成模型必须把这部分视作未核实引用，不得因母版出现某个数字/技能就直接断言为求职者的经历或成就，所有正式写回仍受 RGS 守卫与人工审阅。母版读取失败时退回到现有简历/JD 诊断，不阻断原功能。

本阶段是第一阶段检索增强，不是全面 RAG/向量服务；仅打通 JD 分析与单项优化，不能推断所有 AI 生成入口已完成，也不证明真实服务商的生成准确性或收费情况。详细契约和后续 Embedding 评估条件见 docs/MASTER_EVIDENCE_RETRIEVAL.md。

### 11.24 母版证据采用与现有事实账本联动（2026-11-08）

在母版资料内，用户可以展开 AI 识别候选，点击「核对并采用到当前版本」；流程重新读取本机附件，检查来源未被删除或更新，并且排除摘录与数值不一致、同一字段多材料冲突等异常。只有能够**唯一匹配现有学校或奖项条目**的学历、专业、日期、GPA、排名与奖项等级等部分字段可采用；不创建新学校或奖项，不把加权均分直接写为 GPA，不把单科成绩当作全部主修课程。对原 GPA 字符串中同时包含加权均分时，禁止用一个 GPA 覆盖并丢失另一项成绩口径。界面明确展示旧值、新值及来源，用户主动确认后通过原有 `commitResumeChange` 保存，支持一步撤销。

采用后只修改**当前岗位简历版本**的确定字段，且向已有 `factLedger.version=1` 中写入 `ai-file-extraction` 来源引用、`candidateConfirmed=true`、`status=user-asserted`；绝不设为 `verified-source` 或声称颁证机构认证。保留来源 ID 与非敏感字段描述，不把 PDF/图片、文件名或完整 OCR 引文复制到可导出的简历 JSON；`cloudAllowed=false`，不给模型新增来源元数据的长期发送权限。后续人工编辑对应字段时，现有账本同步将确认标记置为 false；已采用内容因已属于当前简历正式字段，会被既有 JD 匹配和 AI 单项优化使用，但其来源摘录不再作为重复候选发送。母版原件依旧仅保存当前浏览器，删除附件会使已采用字段的来源 ID 失去可定位的原件，删除前提示。

验证包括字段精确匹配、原始数据不可变、幂等、口径隔离、错误候选拒绝、旧来源失效、手工编辑取消采用标记；匿名 Chrome 端到端验证点击采用、账本落地、岗位诊断读取采用值、撤销恢复。当前**不支持**批量自动采用、不支持自动创建新学校/奖项/证书项目、跨版本默默写入或官方真实性认证；与职位不直接匹配的母版内容仍只归档为候选。

### 11.25 结构化证书、奖项、课程成绩与跨岗位显式复用（2026-11-08）

在 11.24 阶段的现有事实账本采用流程基础上，新增三个向后兼容的可选字段：`EducationItem.weightedAverage`、`EducationItem.courseGrades[]` 和 `AwardItem.credentialType`。母版附件和一次性识别缓存仍全局共享；不同岗位版本**仅在用户逐项确认后**独立采用。新证书与奖项的名称允许在原证书与荣誉版块中显式创建；类型、颁发单位、日期和级别结构化维护。课程成绩按学校/课程分别记录，不把加权均分混进 GPA，也不凭一个不存在的分数建立投递结论。

字段识别需有明确来源摘录；学校/奖项名称精确唯一匹配。单科成绩要求非泛称的课程名及 0–100 分值，不能用「课程成绩」这种笼统标签代替科目。证书/奖项等级和时间不能在名称无法唯一匹配时自动新建；赛事年度、证书签发日期、团体/个人荣誉分别保留口径。若材料之间有冲突、来源已变更、字段值与引用摘录不符，禁止直接采用。每次采用通过原撤销栈保存，写入本版本 `factLedger` 来源记录（`user-asserted`、`candidateConfirmed=true`、`cloudAllowed=false`），绝不宣传其为官方认证。后续编辑课程名称或分数会取消原来的采用确认，避免来源与新值错配。

结构化成绩不会未经用户选择被塞入所有模板的 A4 页；版式与旧数据保持兼容。真实模型的提取准确率、跨设备同步、自动把所有课程分数排进投递 PDF、以及新增事实的学籍/官方真伪核验均不在本轮承诺范围。设计契约、字段映射、回归与后续验收见 `docs/STRUCTURED_MASTER_FACTS.md`。

### 11.26 岗位化证据推荐与投递前 RGS 预审（2026-11-08）

在现有「AI 岗位匹配」页新增无需模型调用的岗位化资料建议和「开始投递检查」。推荐器仅对 JD 显式技术术语与当前岗位版本真实存在的项目、结构化成绩、证书和技能进行保守关联，给出现有路径、来源类型和编辑入口，不得自动添加/修改经历，也不向外部模型发送原件。识别不到术语表示信息尚不足，不代表候选人不具备能力。课程成绩依旧默认不进入 A4，须自行决定如何呈现。

投递审查复用既有 ATS 文字导出画布与 buildExportQualityReport，不复制第二套版式逻辑；实施 Q-01 结构与基本联系方式、Q-02 演示与候选来源状态、Q-03 可疑百分比成果、Q-04 有限术语匹配、Q-05 空经历、Q-07 排版预检、Q-08 问题前五项与 Q-09 透明状态。对未实现的子规则、真实 PDF 文字层、实测真实性和海外简历不作合格承诺。状态按 BLOCKED、NEEDS_LAYOUT、REVIEW_REQUIRED 输出；**在实际导出并检查 PDF 前，绝不输出 READY 或「投递就绪」**。报告与当前简历/JD 绑定，修改后必须重新审查。详细契约与缺口见 docs/JOB_SUBMISSION_REVIEW.md。

## 12. 完成定义（DoD）

只有同时满足以下条件，才可声明「规范驱动的简历生成功能完成」：

1. 所有已启用的 AI 入口遵循同一真实性规范并有一致的数据校验；
2. T01–T20 的自动化或可复核实测验收通过，并保留结果；
3. 不存在未经用户批准就将缺失关键词或 AI 推断的经历写入正式简历的路径；
4. AI 失败、无网络、取消、重复提交及旧资料恢复通过回归；
5. 原有模板、单击编辑、拖拽、A4 输出及多版本保持可用；
6. 已验证中文投递 PDF 能正确提取文字，且没有无提示截断；
7. 安全检查表明确记录了第三方上传、凭证保护与公开仓库权限；
8. README 与本规范保持一致；未经过实测的能力标注为待验证。
